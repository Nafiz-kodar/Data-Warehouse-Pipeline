# Data Catalog — Boston Short-Term Rental Data Warehouse

Reference for everyone querying this warehouse. **Gold** is the consumer-facing contract and is
documented column by column. **Silver** is documented at table level, since its column detail lives
in [`scripts/silver/ddl_silver.sql`](../scripts/silver/ddl_silver.sql) and it is not intended for
direct consumption.

Defect identifiers (`D1`–`D15`) refer to [`cleaning_spec.md`](cleaning_spec.md).

---

## Start here

```sql
-- What does a listing cost, where, and how well reviewed is it?
SELECT dl.neighbourhood, dl.room_type,
       count(*)                        AS listings,
       round(avg(f.price_amount), 2)   AS avg_price,
       round(avg(f.review_scores_rating), 2) AS avg_rating
FROM gold.fact_listing_snapshot f
JOIN gold.dim_listing dl USING (listing_key)
WHERE f.is_freshly_scraped          -- see the warning below
GROUP BY 1, 2
ORDER BY avg_price DESC;
```

> ### Read this before aggregating
>
> **Always filter `is_freshly_scraped = true` unless you have a reason not to.** 846 listings (19.3%)
> carry data copied forward from an earlier scrape and average **$146.89** against **$370.77** for
> freshly scraped ones. Including them silently understates every price and availability figure.
>
> **NULL means "not known", never "zero".** 901 listings have no reviews and therefore NULL review
> scores (D11); 685 have no price (D4). Nothing is imputed anywhere in this warehouse, by design —
> so use `avg()`, which skips NULLs, rather than `coalesce(x, 0)`.

## Gold layer — star schema

Two fact tables sharing conformed dimensions, plus one bridge for the amenity many-to-many.
All Gold objects are **views** over Silver, so they are always consistent with the loaded data.

```
                          dim_date
                          |       |
   dim_host ──────> fact_listing_snapshot <────── dim_neighbourhood
      │                (4,414)      ▲                    ▲
      └────────> dim_listing ───────┘                    │
                 (4,414)  │  └──────> fact_review ───────┘
                          │            (252,910)
              bridge_listing_amenity
                          │
                    dim_amenity (1,434)
```

### `gold.dim_listing` — 4,414 rows

One row per listing. The integrated union of both source exports: `LEFT JOIN` from the summary
export (the row superset) onto the detailed export (the column superset), resolving **D5**.

| Column | Type | Description |
|---|---|---|
| `listing_key` | bigint | Surrogate key. Generated by `ROW_NUMBER()`, **not stable across reloads** |
| `listing_id` | bigint | Natural key — the Airbnb listing ID. Use this for joins to external data |
| `listing_name` | text | Listing title |
| `neighbourhood` | text | One of 26 Boston neighbourhoods; joins to `dim_neighbourhood` |
| `room_type` | text | `Entire home/apt` · `Private room` · `Hotel room` · `Shared room` |
| `property_type` | text | 29 values, e.g. `Entire rental unit`. NULL for summary-only listings |
| `accommodates` | integer | Guest capacity |
| `bedrooms` | integer | NULL for 1,261 listings — genuinely unknown |
| `beds` | integer | NULL for 929 listings |
| `bathrooms` | numeric(4,1) | **D8** — 1,030 values recovered by parsing `bathrooms_text`; `0.5` means half-bath |
| `bathrooms_is_derived` | boolean | TRUE where `bathrooms` came from text parsing rather than the source field |
| `latitude` | numeric(9,6) | WGS84. Verified inside its neighbourhood polygon for all 4,414 rows |
| `longitude` | numeric(9,6) | WGS84 |
| `license` | text | Free text: a registration number, `Approved by government`, or an exemption note |
| `has_license` | boolean | Convenience flag — TRUE for 3,150 listings |

### `gold.bridge_listing_amenity` — 155,233 rows

Resolves the many-to-many between listings and amenities (**D7**). Average 35.5 amenities per listing.

| Column | Type | Description |

## Silver layer — cleaned, per source

Silver mirrors the source structure one-to-one (decision A3), so every table traces to exactly one
source file. Integration happens in Gold. Column detail is in
[`ddl_silver.sql`](../scripts/silver/ddl_silver.sql); transform rules are in
[`proc_load_silver.sql`](../scripts/silver/proc_load_silver.sql).

| Table | Rows | Source | Purpose and rules applied |
|---|---:|---|---|
| `silver.summary_listings` | 4,414 | `listings_summary.csv` | Typed summary export. Sole source of the 36 listings absent from detail. D10 drops `neighbourhood_group` |
| `silver.detail_listings` | 4,378 | `listings_detailed.csv` | Typed detailed export — 79 columns from 90 raw. **D9** drops 13 all-NULL columns; applies D1, D2, D8, D12, D13, D14 |
| `silver.detail_reviews` | 252,910 | `reviews_detailed.csv` | Typed reviews with full text. Indexed on `listing_id` and `review_date` |
| `silver.neighbourhoods` | 26 | `neighbourhoods.csv` + `.geojson` | Lookup joined to its boundary. **D15** repairs 4 invalid polygons; GIST index on `geom` |
| `silver.detail_listing_amenity` | 155,233 | `listings_detailed.amenities` | **D7** — the JSON array exploded to one row per listing-amenity pair |

Every Silver table carries `dwh_create_date timestamptz` recording when the row was loaded.

## Bronze layer — raw landing zone

Byte-faithful copy of the source drop. **Every column is `TEXT`**, so a load can never fail on a type
error and raw forms (`$347.40`, `'t'`, JSON-in-a-string) stay inspectable. Do not query Bronze for
analysis — it exists for lineage and reload.

| Table | Rows | Columns |
|---|---:|---:|
| `bronze.summary_listings` | 4,414 | 19 |
| `bronze.detail_listings` | 4,378 | 90 |
| `bronze.detail_reviews` | 252,910 | 6 |
| `bronze.neighbourhoods` | 26 | 2 |
| `bronze.geo_neighbourhoods_raw` | 1 | 1 (`jsonb`, 26 features) |

`reviews_summary.csv` is **not** loaded: its `(listing_id, date)` multiset is provably identical to
`reviews_detailed.csv`, so it carries no information.

## Known limitations

1. **Surrogate keys are not stable.** `ROW_NUMBER()` reassigns keys on every reload. Join on natural
   keys (`listing_id`, `host_id`) when persisting results outside the warehouse.
2. **`estimated_revenue_l365d` is Airbnb's model output**, not observed revenue. Treat it as an
   indicator, not an accounting figure.
3. **One scrape window only.** The fact grain supports history, but only 2026-06-15 → 2026-07-06 is
   loaded, so no trends over time can be computed from `fact_listing_snapshot`.
4. **No calendar or pricing-by-date data** — that file is not in this drop.
5. **Full reload only.** No incremental or CDC loading; both procedures truncate and rebuild.
